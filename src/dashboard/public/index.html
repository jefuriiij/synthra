FAQ · where every number comes from
Understanding your dashboard
Synthra reports what Claude actually used — read from transcripts, not estimated.
Where does Synthra get these numbers from?

Synthra does not estimate token counts — it reads them directly from Claude's own log files. Every number on this dashboard is traceable:

Turns, ↓ In, ↑ Out, Cache R/WParsed from Claude's transcript JSONLs at ~/.claude/projects/<encoded-cwd>/*.jsonl
Model used per turnFrom each turn's model field in the same transcripts
Moat blocks + gate decisionsFrom .synthra-graph/gate_log.jsonl inside each project
Active project, project listFrom ~/.synthra/projects.json (built up as you run syn .)
Total spend (USD)Above token counts × Anthropic's published per-model rates — see "How is cost calculated?" below
Synthra savings (USD)Estimated — see "About the Savings (floor) card" below

The cost-calculation logic lives in src/shared/pricing.ts; the aggregation logic in src/dashboard/delta.ts. Both are linked at the bottom.

What do the columns in Recent Turns mean?
TimeWhen this turn happened (local time)
ProjectWhich directory the turn ran in
ModelClaude model used — Opus, Sonnet, or Haiku (color-coded in the model pill)
InRaw input tokens — brand-new content sent to Claude this turn, not cached
OutTokens Claude generated in its response
Cache R/WCache Read (reused from prior turns) / Cache Write (newly cached for future turns)
CostPer-turn USD estimate using Anthropic's published rates

Why is Raw Input often tiny (e.g. 6 tokens)? Because Claude Code aggressively caches the system prompt, CLAUDE.md, tool definitions, and conversation history. On each turn, only your brand-new message is "raw input" — everything else is a cheap cache read. This is normal and saves significant money.

How is cost calculated?

Each token type has a different per-million-token rate. Synthra uses these rates (defined in src/shared/pricing.ts):

Token typeHaiku 4.5Sonnet 4.xOpus 4.x
Raw Input$1.00/M$3.00/M$15.00/M
Cache Write$1.25/M$3.75/M$18.75/M
Cache Read$0.10/M$0.30/M$1.50/M
Output$5.00/M$15.00/M$75.00/M

Cost = (Input × input rate) + (Output × output rate) + (Cache Read × read rate) + (Cache Write × write rate)

Cache reads are 10× cheaper than raw input. Cache writes are 25% more expensive than raw input. So Claude Code's caching strategy pays for itself quickly across a session.

⚠These are Anthropic API rates, not your plan billing. If you're on Claude Pro, Team, Max, or Enterprise, your actual billing is different — the costs shown are estimates of API-equivalent usage, useful for comparing sessions against each other. See anthropic.com/pricing for the source of these rates.
What is the total context size per turn?

Total context = Raw Input + Cache Read + Cache Write

Example: if Raw Input is 6, Cache Read is 60K, and Cache Write is 13K, your turn used ~73K tokens of context — but 99.99% was efficiently cached, so you only paid the cache-read rate on most of it. The Recent Turns table lets you scan this row by row.

Anthropic's prompt-caching mechanics are documented at docs.anthropic.com/.../prompt-caching.

About the "Savings (floor)" card

This is the only number on the dashboard that's estimated rather than measured. Here's the math:

savings = blocks × 500 tokens × $3 per million input rate

Each time Synthra's PreToolUse hook blocks a Grep or Glob call (because the graph already has high-confidence context), we credit a deliberately conservative 500 tokens at the Sonnet input rate.

It under-counts on purpose because the formula ignores:

  • Cache thrash — the blocked tool result would have been written to the cache at ~125% of the input rate, which we don't count
  • Cascading reads — Claude usually follows a Grep with several Read calls, which the block also prevents but we don't credit
  • Bigger codebases — actual Grep results often exceed 500 tokens by 3–6× in a real repo

Real savings are typically 2–5× the floor. The audit row on the Savings card shows the formula live so you can verify the math.

What is "The Moat"?

"The Moat" is Synthra's PreToolUse hook. Every time Claude Code is about to run a Grep or Glob, the hook calls Synthra's local server first and asks: "do you already have high-confidence context for this query?"

If yes, Synthra returns {"decision":"block"} — Claude can't run the tool. Claude then has to use Synthra's graph tools (graph_continue, graph_read) instead, which return the answer without burning tokens on exploration. This is deterministic enforcement — not prose policy. Claude literally can't disobey.

The Moat card shows total blocks; the inline list below shows the most recent gate decisions (block vs allow) with the originating query.

Every decision is logged to .synthra-graph/gate_log.jsonl for the project.

How does Synthra build the codebase graph?

When you run syn . in a project, Synthra walks the file tree (respecting .gitignore + .synthraignore) and parses each file with tree-sitter WebAssembly grammars. Currently 14 languages are supported:

TypeScript, JavaScript, JSX/TSX, Python, Svelte, Vue, Go, Rust, Java, Kotlin, PHP, Ruby, C/C++, C#, and Dart.

For each file we extract: function and class definitions, exports, imports, and test-to-source links. The output is a structured graph stored at .synthra-graph/info_graph.json with a symbol index at .synthra-graph/symbol_index.json.

The graph is what makes pre-injection and The Moat work — both query it before Claude ever has to Grep.

Where does Synthra store data on disk?

Synthra uses two folders per project, intentionally separated:

.synthra-graph/Gitignored. Heavy generated state — the graph, symbol index, token + gate logs, session info. Rebuilt by syn scan.
.synthra/Git-tracked. Decisions, context notes, branch-scoped memory — the part teammates inherit when they clone the repo.

Plus one global file at ~/.synthra/projects.json that tracks every project on this machine.

How does branch-aware memory work?

Inside .synthra/, context is partitioned by git branch:

  • .synthra/context-store.json — decisions on the default branch
  • .synthra/CONTEXT.md — narrative notes on the default branch
  • .synthra/branches/<sanitized-name>/ — overrides on feature branches

When you switch branches, Synthra's git-watcher (using fs.watch on .git/HEAD) detects the change and reloads the right context. Decisions scoped to a feature branch don't leak back to main until merge.

How does Synthra actually reduce my Claude bill?

Three mechanisms, in order of impact:

  • Pre-injection — at session start, Synthra packs ~4K tokens of graph context (function signatures, top inline bodies, file relationships) into Claude's prompt. Claude doesn't have to Grep / Read to discover what's in the codebase — it already knows.
  • The Moat — the PreToolUse hook deterministically blocks exploratory Grep/Glob when the graph already has high-confidence context. Counts on the Moat card.
  • Branch-aware memory — decisions and CONTEXT notes persist in .synthra/, so Claude doesn't have to be re-told what was decided last session.

The dashboard shows real token counts from Claude's own logs so you can see the effect over time, not just take Synthra's word for it.

Why do long conversations get expensive?

Each turn re-sends the entire conversation history as input. Even cached, the cumulative input grows roughly quadratically:

TurnsPer-turn inputCumulative input
10~2K (mostly cached)~110K
30~2K~930K
50~2K~2.55M

Prompt caching helps a lot (cache reads are 10× cheaper than fresh input), but context still grows. This is why Synthra's pre-injection matters: starting with the answer already in context means you reach a useful state in fewer turns.

Tip: Use /compact in Claude Code or start fresh sessions when a thread feels stale.
